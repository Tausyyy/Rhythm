# Rhythm — план архитектуры

Этот файл описывает целевую структуру проекта. Он добавлен отдельно: исходные файлы проекта не переписывались и не перемещались.

## Принципы
- Существующий код остаётся на своих местах.
- Новые функции добавляются постепенно, по одной вертикали: интерфейс → API-контракт → backend → база данных → тесты.
- Не создавать дублирующие реализации, пока не изучены существующие классы и API.
- Папки `features` группируют код по возможностям приложения, `shared` — переиспользуемый код.
- Заготовки в новых папках не содержат бизнес-логики.

## Frontend — целевая организация

- `src/app` — запуск приложения, маршрутизация и глобальные провайдеры.
- `src/layouts` — общие каркасы страниц (основное приложение и страницы входа).
- `src/features` — отдельные функциональные области: авторизация, главная панель, тренировки, программы, календарь, прогресс, упражнения и подбор программы.
- `src/shared` — общие API-настройки, типы, хуки, утилиты и UI-компоненты.
- `src/assets` — изображения, иконки и другие статические ресурсы (существующая папка сохраняется).

Существующие `App.tsx`, `main.tsx`, `pages`, `components`, CSS и остальные файлы не переносились. Когда будем внедрять архитектуру, сначала разберём их содержимое и решим, что можно переиспользовать.

## Backend — текущие проекты

- `Ritm.Api` — HTTP-точка входа: контроллеры, конфигурация приложения и обработка HTTP.
- `Ritm.Services` — прикладная логика, DTO и преобразование данных.
- `Ritm.Data` — EF Core, сущности, контекст, миграции и начальные данные.
- `Ritm.Tests` — автоматические тесты.

Новые контроллеры и сервисы добавлять в существующие проекты только после проверки текущих DTO, сущностей и методов. Не создавать второй `DbContext`, дублирующие сущности или параллельный API без необходимости.

## Предлагаемый порядок разработки
1. Разобрать текущий frontend и закрепить базовую маршрутизацию/общий layout.
2. Проверить существующую авторизацию и подключение API.
3. Сделать Dashboard вместе с необходимыми endpoint'ами.
4. Реализовать Workouts и Programs, переиспользуя существующие сущности и сервисы.
5. Подключить Calendar и Progress на основе фактической модели данных.
6. Доработать Exercises и подбор программы/Quiz.
7. Добавить валидацию, обработку ошибок, адаптивность и тесты.
8. Провести интеграционную проверку всего приложения.

## Важно
Это план и каркас, а не обещание, что каждая перечисленная функция уже реализована. Названия и связи уточняются по мере чтения существующего кода.
